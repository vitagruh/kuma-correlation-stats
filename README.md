# KUMA daily stats

Ежедневный анализ сработок правил корреляции Kaspersky KUMA: сбор через REST API v3,
история в SQLite, поиск аномалий, HTML-отчёт с графиками, CSV/JSON и уведомления.

Программа рассчитана на запуск раз в сутки по расписанию: анализирует истекшие
локальные сутки, сравнивает их с историей и складывает отчёт в архив.

---

## Возможности

- **Сбор за сутки** через `POST /api/v3/events` с SQL-запросами: всего сработок,
  распределение по правилам, критичности, тактикам MITRE, тенантам, источникам,
  учётным записям и хостам, почасовая динамика.
- **История и аномалии**: SQLite-база по дням, среднее/σ/медиана/максимум, z-score,
  флаги `новое`, `рост`, `падение`, `шум`, список молчащих правил.
- **HTML-отчёт** с инлайновыми SVG-графиками (без интернета и внешних библиотек):
  KPI, аномалии, топ правил, динамика по часам, тепловая карта «правило × час»,
  критичность, тактики, разрезы, история, приложение с журналом запросов.
- **CSV для Excel** (`utf-8-sig`, разделитель `;`) и JSON-снимок для повторной
  сборки отчёта командой `render`.
- **Уведомления**: SMTP (текст + вложение HTML) и webhook JSON; опционально
  только при наличии аномалий.
- **Устойчивость**: повторные попытки при 429/5xx, переавторизация, резервные
  запросы без `Severity`, восстановление списка правил и почасовой динамики по
  сырым событиям, предупреждения о качестве данных прямо в отчёте.
- **Только стандартная библиотека Python** — удобно для закрытого контура.

## Требования

- Python 3.10+.
- Сетевой доступ к KUMA REST API (обычно `https://<kuma>:7223`) и права на чтение
  событий, кластеров, тенантов и, при необходимости, ресурсов.
- Для корректных часовых поясов на Windows желательно поставить `tzdata`
  (`pip install tzdata`). Без него используется фиксированный сдвиг из конфига,
  и переход на летнее время не учитывается — в отчёт добавляется предупреждение.

Внешних обязательных зависимостей нет.

## Быстрый старт

```bash
# 1. Шаблон конфигурации
python -m kuma_stats -c config.json init-config

# 2. Укажите kuma.base_url, токен, при необходимости timezone/output_dir/state_dir
#    и проверьте доступы
python -m kuma_stats -c config.json check

# 3. Сбор за предыдущие сутки
python -m kuma_stats -c config.json run
```

Готовый пример со всеми параметрами — [config.example.json](config.example.json).

### Токен KUMA

Токен выпускается в интерфейсе KUMA (профиль пользователя → API-токены; в разных
версиях путь может отличаться). Можно использовать любой из способов:

1. `kuma.token` — токен прямо в конфиге;
2. `kuma.token_file` — путь к файлу с токеном (удобнее для прав доступа);
3. `kuma.username` + `kuma.password` — вход через `/api/v1/login`;
4. переменная окружения `KUMA_TOKEN` — переопределяет значение из конфига.

Пароль SMTP можно передать через `SMTP_PASSWORD`, пароль KUMA — через
`KUMA_PASSWORD`.

Требуемые права: чтение событий и служебных сущностей. Для инвентаря правил
(`collect_rule_inventory=true`) нужен доступ к `/resources?kind=correlationRule`.

### TLS

По умолчанию сертификат проверяется. Если KUMA использует внутренний CA:

```json
"kuma": {
  "verify_tls": true,
  "ca_bundle": "C:/certs/kuma-ca.pem"
}
```

Отключение проверки (`verify_tls: false`) допустимо только в доверенном контуре;
программа выводит предупреждение в лог и в отчёт.

## Команды

| Команда | Назначение |
|---|---|
| `check` | Проверить токен, кластеры, тенанты, запрос событий и права на каталоги. |
| `run` | Собрать данные за сутки, обновить историю, построить отчёт, отправить уведомления. |
| `render` | Перестроить отчёт из `snapshot.json` (например, после изменения шаблона или истории). |
| `daemon` | Крутить сбор ежедневно в заданное локальное время (`--at 01:00`). |
| `init-config` | Создать шаблон JSON-конфигурации. |

Полезные параметры `run`:

```bash
python -m kuma_stats -c config.json run --date 2026-10-06   # конкретная дата
python -m kuma_stats -c config.json run --no-store          # без истории (аномалий не будет)
python -m kuma_stats -c config.json run --no-notify         # без email/webhook
python -m kuma_stats -c config.json run --fail-on-anomaly   # код 5 при аномалиях
python -m kuma_stats -c config.json run --output-dir D:\reports
```

`render` без аргумента берёт самый свежий снимок из `report.output_dir`:

```bash
python -m kuma_stats -c config.json render
python -m kuma_stats -c config.json render reports/2026-10-06
python -m kuma_stats -c config.json render reports/2026-10-06/snapshot.json --out D:\tmp\report.html
```

### Коды возврата

| Код | Значение |
|---|---|
| 0 | Успех. |
| 1 | Непредвиденная ошибка. |
| 2 | Ошибка конфигурации или аргументов. |
| 3 | Ошибка доступа/сети KUMA. |
| 4 | Не удалось построить отчёт. |
| 5 | Найдены аномалии при `--fail-on-anomaly`. |

## Запуск по расписанию

### Linux: cron

```cron
CRON_TZ=Europe/Moscow
0 1 * * * cd /opt/kuma-stats && /usr/bin/python3 -m kuma_stats -c config.json run >> state/cron.log 2>&1
```

`CRON_TZ` должен совпадать с `report.timezone`, иначе «предыдущие сутки» будут
определяться по другому часовому поясу.

### Linux: systemd timer

`/etc/systemd/system/kuma-stats.service`:

```ini
[Unit]
Description=KUMA daily correlation stats
After=network-online.target

[Service]
Type=oneshot
User=kuma-stats
WorkingDirectory=/opt/kuma-stats
ExecStart=/usr/bin/python3 -m kuma_stats -c /opt/kuma-stats/config.json run
```

`/etc/systemd/system/kuma-stats.timer`:

```ini
[Unit]
Description=Run KUMA stats daily

[Timer]
OnCalendar=*-*-* 01:00:00
Persistent=true
RandomizedDelaySec=300

[Install]
WantedBy=timers.target
```

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now kuma-stats.timer
```

### Windows: Планировщик заданий

Рабочий каталог у задачи по умолчанию — `System32`, поэтому относительные
`output_dir`/`state_dir` лучше заменить на абсолютные или использовать обёртку
`run.cmd`:

```bat
@echo off
cd /d C:\kuma-stats
C:\Python312\python.exe -m kuma_stats -c config.json run
```

```bat
schtasks /Create /TN "KUMA daily stats" /SC DAILY /ST 01:00 ^
  /TR "C:\kuma-stats\run.cmd"
```

Проверка: `schtasks /Run /TN "KUMA daily stats"`, журнал — в
`state\kuma_stats.log` и `state\kuma_stats.log.1`… (ротация 5 × 5 МБ).

### Встроенный демон

Если планировщик недоступен:

```bash
python -m kuma_stats -c config.json daemon --at 01:00 --run-now
```

Демон переживает ошибки отдельных запусков и продолжает работу на следующий день.
Для промышленной эксплуатации предпочтительнее cron/systemd/Планировщик.

## Что в отчёте

1. **Шапка**: период, часовой пояс, кластер, время формирования.
2. **KPI**: сработки, среднее, правила, источники, аномалии, новые правила,
   пиковый час, базовые события Type=1.
3. **На что обратить внимание**: предупреждения о качестве данных, отклонение
   общего объёма, состояние истории.
4. **Аномалии и новые правила**: таблица с Δ, z-score, числом дней сработок, флагами.
5. **Топ правил**: диаграмма и таблица с долей, динамикой, критичностью.
6. **Динамика по часам**: линия, ночная доля, тепловая карта топ-25 правил.
7. **Критичность, MITRE-тактики, приоритеты**.
8. **Разрезы**: источники, учётные записи, назначения, хосты.
9. **Тенанты** (если есть данные).
10. **Правила без сработок** по истории и **инвентарь** правил (если включён).
11. **История**: график и таблица последних дней.
12. **Приложение**: ссылки на CSV/JSON, журнал SQL-запросов с длительностью и
    ошибками, описание методики.

| `kuma.token` / `token_file` / `username`+`password` | — | Доступ к API. |
| `kuma.verify_tls` / `ca_bundle` | `true` / `""` | Проверка TLS и внутренний CA. |
| `kuma.cluster_id` / `cluster_name` | `""` | Если кластеров несколько, выбор обязателен. |
| `kuma.event_type` | `3` | 1 — базовые, 2 — агрегированные, 3 — коррелированные. |

| `kuma.hourly_breakdown` | `true` | 24 запроса по часовым срезам. |

| `kuma.raw_events_limit` | `20000` | Лимит выборки сырых событий. |
| `kuma.collect_rule_inventory` | `false` | Запрос списка правил корреляции. |
| `report.timezone` | `Europe/Moscow` | Локальные сутки и подписи графиков. |
| `report.utc_offset_hours` | `3.0` | Резервный сдвиг, если нет базы IANA. |

| `report.day_offset` | `1` | На сколько дней назад смотреть при `previous_day`. |
| `report.output_dir` | `./reports` | Каталог отчётов. |
| `report.state_dir` | `./state` | История и логи. |

| `baseline.min_days` | `7` | Минимум дней для аномалий. |

не привела к тихой работе с настройками по умолчанию.

## Методика

- **Период**: локальные сутки `[00:00, 24:00)` в `report.timezone`; в API границы
  включительные, поэтому конец передаётся как `23:59:59.999`.
- **История**: SQLite, ключ `(день, кластер)`. Повторный запуск за тот же день
  заменяет запись. Базовая выборка для сравнения — предыдущие `baseline.days`
  дней, текущий день в неё не входит.
- **Среднее и z-score**: `z = (count − mean) / σ`, где σ — генеральное
  стандартное отклонение по истории. Если σ = 0, используется ±99.
- **Флаги правила**:
  - `новое` — правило не встречалось в истории, но есть сегодня;
  - `рост` — `z ≥ z_threshold`, `count ≥ min_events`, прирост ≥ `min_delta`;
  - `падение` — `z ≤ −z_threshold`, среднее ≥ `min_events`, падение ≥ `min_delta`;
  - `шум` — объём ≥ `noise_min_events`, стабильно повторяется, Δ в пределах
    `±noise_max_delta_pct` и нет других флагов;
  - `молчит` — правило было активным в истории, но сегодня отсутствует
    (при достаточной истории и неусенном списке правил).
- **Аномалия общего объёма** — `|z| ≥ z_threshold` **и**
  `|Δ| ≥ total_min_delta_pct`.
- **Первые отчёты** не содержат аномалий, пока не накоплено `min_days` дней.

### Ограничения

- История ведётся по **названию правила**. Переименование правила в KUMA начнёт
  новую историю (ID сохраняется в CSV, но не используется как ключ).
- Первые `min_days` запусков — только накопление истории.
- z-score чувствителен к выбросам и не учитывает день недели; для зрелой
  эксплуатации стоит перейти на медиану/MAD и недельную сезонность (см. идеи).
- При усечении выборки (лимиты `max_rule_rows`, `raw_events_limit`,
  `hourly_rules_limit`) часть метрик строится по выборке, о чём сообщается в
  предупреждениях. Уникальные источники и детали правил — всегда по выборке.
- Список ресурсов KUMA не содержит флага «включено/выключено», поэтому раздел
  инвентаря носит информационный характер.
- Отчёт содержит IP-адреса и учётные записи — это чувствительные данные.

## SQL и API

Используются стандартные запросы KUMA (диалект SQL из документации):

```sql
SELECT count(ID) FROM `events` WHERE Type = 3;

SELECT count(ID), Name, Severity FROM `events`
WHERE Type = 3 GROUP BY Name, Severity ORDER BY count(ID) DESC LIMIT 1000;

SELECT count(ID), Severity FROM `events`
WHERE Type = 3 GROUP BY Severity ORDER BY count(ID) DESC;

SELECT count(ID), Name FROM `events`
WHERE Type = 3 GROUP BY Name ORDER BY count(ID) DESC LIMIT 250;  -- на каждый час
```

Эндпоинты: `POST /api/v3/events`, `GET /api/v3/events/clusters`,
`GET /api/v3/tenants`, `GET /api/v3/resources?kind=correlationRule`,
`GET /api/v3/users/whoami`, при входе по паролю — `POST /api/v1/login`.

Если KUMA не разрешает `Severity` в `GROUP BY`, автоматически выполняется
упрощённый запрос, а критичность добирается из сырых событий.

## Диагностика

```bash
python -m kuma_stats -c config.json check --inventory
```

Типичные ситуации:

- **401** — истёк или неверен токен; при логине/пароле KUMA могла не поддержать
  `/api/v1/login` — используйте API-токен.
- **403** — у учётной записи нет прав на события/ресурсы.
- **TLS certificate verify failed** — укажите `ca_bundle` или (осознанно)
  `verify_tls: false`.
- **«Часовой пояс недоступен»** — поставьте `tzdata`; до этого используется
  фиксированный сдвиг `utc_offset_hours`.
- **Пустой отчёт** — проверьте `Type` (по умолчанию 3), период и часовой пояс;
  предупреждение о нуле базовых событий Type=1 указывает на проблемы сбора.
- **Несколько кластеров** — задайте `cluster_id` или `cluster_name`.

Лог пишется в консоль и (если задан `logging.file`) в файл с ротацией.

## Безопасность

- Токен не попадает в отчёт, снимок, CSV и журнал запросов. Храните его в
  `token_file` с ограниченными правами или в переменной `KUMA_TOKEN`.
- Отчёты и снимки содержат чувствительные данные; ограничьте доступ к
  `report.output_dir` и не отправляйте их во внешние сервисы без необходимости.
- Webhook отправляется по HTTPS с проверкой сертификата; SMTP — по вашему
  внутреннему серверу. Вложение HTML содержит те же чувствительные данные.
- Программа не выполняет исходящих запросов, кроме KUMA, SMTP и webhook.

## Идеи развития

Уже реализовано: суточный срез, история, z-score-аномалии, молчащие правила,
инвентарь, часовые срезы, тепловая карта, разрезы, MITRE-тактики, CSV/JSON,
архив, email/webhook, демон, резервные запросы.

Ближайшие улучшения:

1. **Готовые интеграции** с Telegram/Teams/Slack (форматирование под мессенджер,
   кнопка «открыть отчёт»), а не только generic webhook.
2. **Недельная и месячная сводка**: сравнение неделя-к-неделе, тренд 30/90 дней,
   top movers за период.
3. **Подавление известного шума**: список правил/исключений, чтобы «шумные»
   правила не засоряли аномалии, с отметкой «в отпуске/на обслуживании».
4. **Карточка правила**: top-источники, top-хосты, первое/последнее событие,
   уникальные пользователи (пары «правило × источник» уже собираются).
5. **Ссылки на KUMA**: deep link в поиск событий по правилу и периоду.
6. **XLSX-экспорт** (опционально `openpyxl`) и компактный PDF для руководства.

Средние по сложности:

7. **Устойчивая база**: медиана/MAD вместо среднего/σ, сезонность по дню недели
   и часу, EWMA; меньше ложных срабатываний на редких правилах.
8. **Оценка качества правил**: индекс шумности, стабильность, дубликаты,
   правила-«соседи», рекомендации по порогам и агрегации.
9. **Карта покрытия MITRE ATT&CK**: тактики/техники в сработках, пробелы покрытия,
   сравнение с базовым потоком Type=1.
10. **Мультикластерность и тенанты**: сравнение площадок, отдельные отчёты и
    пороги для тенантов, сводный дашборд.
11. **Мониторинг здоровья**: отсутствие данных, падение базового потока,
    задержка корреляции, недоступность API — отдельные алерты.
12. **Объяснение аномалий**: вклад правил/источников в отклонение общего объёма,
    автоматическая формулировка «почему выросло».

Перспективные:

13. **Веб-дашборд** с фильтрами по правилу/тенанту/хосту и drill-down.
14. **SOAR-интеграция**: автосоздание тикетов (Jira/TheHive) по критичным
    аномалиям с дедупликацией.
15. **Метрики в Grafana/Prometheus** (pushgateway) для долгосрочных трендов.
16. **Прогноз и ёмкостное планирование**: ожидаемый объём, оценка роста лицензий
    и нагрузки на коррелятор.
17. **LLM-резюме смены** в полностью офлайн-режиме (локальная модель) — только
    как дополнение к детерминированным метрикам.

config.example.json
pyproject.toml
requirements.txt
